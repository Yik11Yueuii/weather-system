# Weather 微服务 JMeter 压力测试计划

## 一、环境准备

### 启动顺序
```
1. Redis (127.0.0.1:6379)
2. Eureka Server (9001)
3. CityList (9300)
4. QueryData (9200)
5. CacheJob (9100) — 可选，压测时不启动以免干扰
6. Zuul Gateway (6001)
```

### 启动命令
```bash
# 各模块在IDEA中分别启动，或使用：
cd D:\workplace\huaweipro
mvn spring-boot:run -pl hanshidemo-weather-citylist9300
mvn spring-boot:run -pl hanshidemo-weather-querydata9200
mvn spring-boot:run -pl hanshidemo-weather-cache9100
mvn spring-boot:run -pl hanshidemo-service-zuul6001
```

### 验证正常
```bash
# 直接调微服务
curl http://localhost:9200/query/weather/cache/101020100
curl http://localhost:9300/city/list

# 经Zuul网关
curl http://localhost:6001/weatherhanshi/weather/101020100
curl http://localhost:6001/weatherhanshi/tabCity/CityList
```

## 二、JMeter 线程组配置

### 通用设置
- **Ramp-up Period**: 10秒（逐步加压）
- **循环次数**: 勾选"永远" 或 设置持续时间
- **持续时间**: 各场景不同（见下表）

### HTTP请求默认值
- **协议**: http
- **服务器IP**: localhost
- **端口号**: 6001（经Zuul网关）/ 9200（直连QueryData）/ 9300（直连CityList）
- **编码**: UTF-8

## 三、测试用例详细设计

### TC-01: 缓存命中压测（核心场景）
| 项目 | 值 |
|------|-----|
| **接口** | GET `/weatherhanshi/weather/101020100` |
| **目标** | Zuul (6001) |
| **前提** | Redis中已有 `weather_cache:101020100` 缓存 |
| **阶梯** | 50→200→500 线程，每阶梯120s |
| **断言** | 响应码=200，响应体包含 `"code":200` |
| **目标QPS** | > 500/s |
| **目标延迟** | P99 < 500ms |

### TC-02: 穿透API压测
| 项目 | 值 |
|------|-----|
| **接口** | GET `/query/weather/api/101020100` |
| **目标** | QueryData (9200) 直连 |
| **前提** | 每次调用真正的第三方API |
| **阶梯** | 10→20→50 线程 |
| **断言** | 响应码=200 |
| **目标延迟** | P99 < 3000ms |
| **注意** | ⚠️ 不要开太高并发，第三方API有限流 |

### TC-03: 城市列表查询
| 项目 | 值 |
|------|-----|
| **接口** | GET `/city/list` |
| **目标** | CityList (9300) 直连 |
| **阶梯** | 100→500 线程 |
| **断言** | 响应码=200，响应体是JSON数组 |
| **目标延迟** | P99 < 300ms |
| **前提** | 首次查DB，后续走Redis缓存 |

### TC-04: 全链路（经Zuul网关）
| 项目 | 值 |
|------|-----|
| **接口** | GET `/weatherhanshi/weather/101020100` |
| **目标** | Zuul (6001) |
| **阶梯** | 100→300→500 线程 |
| **断言** | 响应码=200 |
| **目标延迟** | P99 < 600ms |
| **说明** | 包含网关转发开销 |

### TC-05: 多城市并发（模拟真实场景）
| 项目 | 值 |
|------|-----|
| **接口** | GET `/weatherhanshi/weather/${cityId}` |
| **目标** | Zuul (6001) |
| **参数化** | CSV读取城市列表: 101020100,101030100,101040100,... |
| **线程数** | 200 |
| **目标延迟** | P99 < 800ms |
| **目的** | 验证不同城市缓存分布均匀 |

### TC-06: Hystrix熔断验证 ⚡
| 项目 | 值 |
|------|-----|
| **接口** | GET `/query/weather/api/101020100` |
| **目标** | QueryData (9200) |
| **前提** | **断开网络** 或 故意给错误URL |
| **线程数** | 50，持续30s |
| **断言** | 响应码=200，响应体包含 `"code":500` 或 `"服务繁忙"` |
| **目的** | 验证Hystrix降级生效 |

### TC-07: 混合压测
| 项目 | 值 |
|------|-----|
| **场景** | 线程组1: 天气查询 150线程 |
|       | 线程组2: 城市列表 50线程 |
| **目标** | Zuul (6001) |
| **目的** | 验证两个服务互不干扰 |

### TC-08: 长时间稳定性
| 项目 | 值 |
|------|-----|
| **接口** | GET `/weatherhanshi/weather/101020100` |
| **目标** | Zuul (6001) |
| **线程数** | 100 |
| **持续时间** | 10分钟 |
| **断言** | 错误率 < 0.1% |
| **目的** | 检查内存泄漏、连接池耗尽 |

## 四、JMeter 监听器建议

1. **聚合报告** — 查看平均/中位数/P99/吞吐量
2. **汇总图** — 实时观察吞吐量曲线
3. **响应时间图** — 观察延迟抖动
4. **TPS图** — 观察吞吐拐点
5. **查看结果树** — 仅调试时开启，压测时关闭

## 五、预期结果

| 指标 | 缓存命中 | 穿透API | 城市列表 | 全链路 |
|------|---------|---------|---------|--------|
| **并发50** | < 100ms, 0%错误 | < 2000ms, 0%错误 | < 50ms, 0%错误 | < 150ms |
| **并发200** | < 200ms, 0%错误 | < 3000ms, < 1%错误 | < 100ms, 0%错误 | < 300ms |
| **并发500** | < 500ms, < 0.1%错误 | 不建议 | < 200ms, 0%错误 | < 600ms |
| **并发1000** | < 1000ms, < 1%错误 | 不建议 | < 500ms, 0.1%错误 | < 1200ms |

## 六、压测结论判断标准

✅ **通过**: 500并发下 P99 < 500ms, 错误率 < 0.1%  
⚠️ **警告**: 500并发下 P99 > 1000ms 或错误率 > 1%  
❌ **失败**: 200并发下 P99 > 2000ms 或错误率 > 5%
